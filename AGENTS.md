# AGENTS.md

Rules for AI coding agents working in this repository. People should read
[CONTRIBUTING.md](CONTRIBUTING.md); everything here applies to them too. The
`PR rules` check enforces the rules marked (checked); a pull request that
breaks one cannot be merged.

## What hertzhound is

A pure Dart library and CLI that finds the real audio format and duration of
a file from its header bytes. The parsers live in `lib/src/` (`wav.dart`,
`flac.dart`, `mp3.dart`, `aiff.dart`, `mp4.dart`, dispatched by `sniff.dart`);
`dart:io` helpers, including `PlaybackAliases`, live in `lib/src/io/`; the CLI
is `bin/hertzhound.dart`. The package is in maintenance: new features are on
hold.

Read before you touch:

- a parser: the "Ground rules" section of CONTRIBUTING.md, `doc/formats.md`,
  and the synthetic corpus in `test/support/writers.dart` and
  `test/support/build.dart`.
- byte reads: `ByteReader` in `lib/src/bytes.dart` (it enforces the per-probe
  read budget) and the fuzzer in `test/support/fuzz.dart`.
- the public API or the CLI: `doc/api.md`, `lib/hertzhound.dart` and
  `lib/hertzhound_io.dart`.

## Commands

Use the Dart SDK, 3.8 or newer. Every one of these must pass before you open
or update a pull request. CI runs the same ones:

```bash
dart pub get
dart format --output=none --set-exit-if-changed .
dart analyze --fatal-infos
dart test --reporter=expanded                    # includes a bounded fuzz run
dart test --platform chrome --reporter=expanded  # dart:io tests are skipped
dart pub publish --dry-run
dart run example/main.dart
```

Run one test file while iterating: `dart test test/wav_test.dart`.

## Stop and ask the human

Some things must come from the real world. An agent must never invent them.
Stop and ask the person you work for to provide them:

- **What a real program writes.** A layout "as written by" an encoder, DAW or
  phone, or what `afinfo`, `ffprobe` or a player reports for it, must come
  from a real file the human produced and ran the tools on. See
  `test/aifc_fixture_test.dart`: the commands and the tool output are kept
  next to the fixture. Never invent such output.
- **The specification.** Cite the exact section of the public spec (RIFF/WAVE,
  EBU Tech 3306, the FLAC format specification, ISO/IEC 11172-3 and 13818-3,
  AIFF and AIFF-C, ISO/IEC 14496-12) for every field offset, table entry and
  factor. Never invent a bitrate table value, a frames-per-packet factor or a
  clause number. If you cannot confirm a factor, the codec gets no duration
  (see the unconfirmed AIFF-C codecs in `doc/formats.md`); say so.
- **Player behaviour.** Claims about just_audio, ExoPlayer/Media3 or AVPlayer
  need a real run on a stated device and version, or a cited source.
- **An accepted issue.** If the change has no issue labelled `accepted`, stop
  and ask the human to open one and wait for a maintainer.

## Code

- **English only** for code, identifiers, comments, commit messages and docs.
  Answer the person you work for in their language.
- Target the minimum SDK in `pubspec.yaml` (Dart 3.8). Do not use language or
  library features newer than that.
- Parsers never throw on input, bound every loop, read only through
  `ByteReader`, and never report a guess as exact.
- Web-safe arithmetic in `lib/`: no shifts into bit 31 or above, no 64-bit
  masks. `dart:io` only in `lib/src/io/` and `bin/`.
- Public API has doc comments (`public_member_api_docs`). Other comments are
  sparse: only where the code is not self-evident. Do not add comments, doc
  comments or type annotations to code you did not change.

## Tests (checked)

- Every change to `lib/` or `bin/` comes with a test change under `test/`. A
  bug fix has a test that fails without the fix; check that it does before
  you open the pull request.
- Fixtures are generated byte by byte in `test/support/`; a new layout is a
  new builder in `test/support/writers.dart`. Never add audio files: the only
  binary fixture is real encoder output the maintainer recorded.
- Tests that need `dart:io` are marked `@TestOn('vm')`; everything else must
  also pass in Chrome.

## Never

- Never silence the analyzer (checked): no `// ignore:`,
  `// ignore_for_file:`, no changes to `analysis_options.yaml`. Fix the
  finding instead.
- Never delete, skip, loosen or rewrite an existing test, expectation,
  fixture or fuzz bound to make CI pass. If a test looks wrong, say so in the
  issue.
- Never change what users depend on: the names of `AudioFormat`,
  `DurationAccuracy` and `ProbeNote` values, the `sniff*` signatures and
  `AudioProbe` fields, the CLI output and exit codes (1 when an extension
  lies, 2 when a file cannot be read), or the `hertzhound-` copy prefix and
  `hertzhound_playback` folder of `PlaybackAliases`.
- Never bump the version in `pubspec.yaml`, edit a released `CHANGELOG.md`
  section, publish, tag or release. Add your entry at the top of
  `CHANGELOG.md` under `## Unreleased` (create the heading if it is missing).
- Never add a dependency (the package has none) or change CI workflows unless
  the issue asks for it.
- Never add unrelated "improvements": no drive-by refactors, renames,
  reformatting of untouched code or dead code.
- Never open pull requests, issues or comments on your own. The human reviews
  your work and posts it.

## Pull requests (checked)

- First an issue, labelled `accepted` by a maintainer. The pull request says
  `Closes #N`.
- One issue per pull request, at most 400 changed lines.
- At most 2 open pull requests per person.
- Fill in the pull request template, including `### AI use` with the tool and
  model.
- The person submitting has read, run and understood every line, and writes
  the description in their own words. Pull requests that are raw, unreviewed
  agent output will be closed.
