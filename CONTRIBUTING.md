# Contributing

Thanks for helping. Bug reports with a file layout that confuses the parser
are the most valuable contribution of all.

## Reporting a file that is read wrongly

Please do **not** attach copyrighted audio. Describe the structure instead,
or attach only the header:

```sh
head -c 4096 suspect.wav | xxd > header.txt
```

For a WAV or AIFF, the chunk order and sizes are usually enough. Say which
program wrote the file, what this package reported, and what the right
answer is.

## Development

```sh
dart pub get
dart format .
dart analyze --fatal-infos
dart test
dart pub publish --dry-run
dart run tool/fuzz.dart --iterations 200000   # optional, longer fuzzing
```

CI runs these on the minimum supported SDK (3.8.0) and on stable, with
`dart format --output=none --set-exit-if-changed .` (on stable only) in place
of `dart format .`. It also runs the web-safe tests in Chrome
(`dart test --platform chrome`) and `dart run example/main.dart`.

## AI-assisted contributions

Using AI tools is fine; please just be open about it.

- Say in the PR description which AI tools you used, if any: none, some or
  most, plus the tool or agent and the model (for example "Claude Code,
  Opus 5.5" or "Copilot, GPT-5").
- Please write the PR description in your own words; short and plain is fine.
  It shows us what you understood about the change. Please don't paste
  generated text.
- Read, run and test every line you submit, and be ready to explain it in
  review. If you don't understand what a line does, don't submit it.
- Keep the change focused. Agents like to add unrelated "improvements",
  long comments and dead code; remove them before you open the pull request.
- Pull requests that are raw, unreviewed agent output will be closed.
- If you use an agent, point it at [AGENTS.md](AGENTS.md).
- If the disclosure is missing, a check adds a reminder to the PR. It does
  not fail the PR, but a maintainer will ask about it before merging.

## Ground rules

- **Clean-room.** Work from the public specifications (RIFF/WAVE, EBU Tech
  3306, the FLAC format specification, ISO/IEC 11172-3 and 13818-3, AIFF and
  AIFF-C, ISO/IEC 14496-12). Do not paste code from other parsers.
- **Synthetic fixtures only.** Test files are generated byte by byte in
  `test/support/`. A new real-world layout becomes a new builder in
  `test/support/writers.dart`.
- **Never throw on input.** Parsers bounds-check every read and return
  `AudioFormat.unknown` or a probe without a duration when unsure. A guess is
  never reported as exact.
- **Web-safe arithmetic.** No shifts into bit 31 or above and no 64-bit
  masks in `lib/`; multiply instead, so results are identical on the VM and
  in JavaScript.
- **Bounded reads.** Every loop has a fixed upper bound, and every read goes
  through `ByteReader`, which enforces the per-probe budget.
- Keep the public API documented; `dart analyze` enforces
  `public_member_api_docs`.

## Pull requests

Small, focused commits with clear messages, in English. Run the commands
above before pushing; every CI check must pass before a pull request can be
merged. The `PR rules` check enforces these:

- **Issue first.** Open an issue and wait until a maintainer labels it
  `accepted`, then write `Closes #N` in the pull request.
- **Tests.** Every change to `lib/` or `bin/` needs a test change under
  `test/`. A bug fix needs a test that fails without the fix.
- **Small.** At most 400 changed lines, one issue per pull request.
- **No suppressions.** No `// ignore:`, no `// ignore_for_file:`, no changes
  to `analysis_options.yaml`. Fix the finding.
- **At most 2 open pull requests** per person.

If a rule really does not fit your change, say why in the description. A
maintainer can waive it with a label (`no-tests-needed`, `large-change` or
`suppression-ok`).
